PR #362 · feat/can-dsl-phase2a

Code-first CAN DSL

What changed, why, and how it works — a guided tour of Phase 2a.

The one-sentence version: every CAN message's byte layout used to be written down in three independent places that could silently disagree; now it's written once in a .def file, and the C++ encoder, decoder, and DBC all come out of it.

1 · The problem we were living with

A CAN message like 0x4A0 AMS_status needs its byte layout known in several spots: the firmware encoder (struct → 8 bytes on the wire), a decoder, and the DBC file (docs/dbc/ams.dbc) that the ECU & dashboard read to understand our frames. Each of those was hand-written separately.

The silent trap. The DBC is produced by tools/gen_dbc.py — 722 lines of Python that re-declare every layout by hand. Our CI check "DBC matches generator" only verifies Python ↔ committed DBC. Nothing ever checked that the Python matched the actual C++ encoders. So if you edited a byte in the C++ encoder and forgot the Python, CI stayed green while the DBC quietly started lying about the firmware — and this cycle alone, 0x135, 0x4A2 and 0x4A0 all got edited.

2 · The idea — one declaration, four artifacts

Declare each message's layout once, in a tiny .def file. Here is the entire declaration of 0x4A0: 

CAN_MSG(AMS_status, 0x4A0, 8, "AMS", 500)
    FIELD_LE (fsm_state,            uint8_t,  0,  8, 1, 0, "enum")
    FIELD_LE (ams_ok,               uint8_t,  1,  8, 1, 0, "bool")
    FIELD_LE (module_online_mask,   uint8_t,  2,  8, 1, 0, "bitmask")
    FIELD_LE (reserved_b3,          uint8_t,  3,  8, 1, 0, "")
    FIELD_BE (min_cell_mV,          uint16_t, 4, 16, 1, 0, "mV")
    FIELD_BE (max_cell_mV,          uint16_t, 6, 16, 1, 0, "mV")
CAN_MSG_END(AMS_status)

Args: (name, C-type, byte index, bit length, factor, offset, unit). FIELD_LE = little-endian, FIELD_BE = big-endian (Motorola, the DBC sawtooth), and the signed variants FIELD_LE_S / FIELD_BE_S.

That single block is read four times by can_codecs.hpp, each time with different macro definitions (a classic X-macro), producing four things that can never drift apart:

ams_status.def
→
① typed struct
② encode_*()
③ decode_*()
④ DBC FieldDesc[]

Add a field, change a width, flip endianness → you edit one line and the struct, the encoder, the decoder, and the DBC row all move together. There is no second source of truth left to forget.

How the X-macro passes work

The same .def is #included under different meanings of FIELD_LE:

// pass 1 — make a struct member
#define FIELD_LE(name,ctype,byte,len,f,o,u)  ctype name {};

// pass 2 — make the encoder body
#define FIELD_LE(name,ctype,byte,len,f,o,u) \
    can_dsl::set_le(d, 8u*(byte), len, static_cast<uint64_t>(in.name) & MASK(len));

// pass 3 — make the decoder body        // pass 4 — make a DBC descriptor row
#define FIELD_LE(...) out.name = get_le(...);   { #name, 8u*byte, len, /*LE*/false, ... }

3 · What actually changed in the firmware

The live telemetry encoders are now thin adapters over the generated code. Same function signature, so the safety task's call site didn't change a character:

Before — hand bit-twiddling

Frame encode_status(state, ams_ok, bms){
  Frame f={};
  f[0]=state;
  f[1]=ams_ok?1:0;
  f[2]=bms.module_online_mask;
  f[3]=0;
  f[4]=bms.min_cell_mV>>8;   // BE hi
  f[5]=bms.min_cell_mV&0xFF; // BE lo
  f[6]=bms.max_cell_mV>>8;
  f[7]=bms.max_cell_mV&0xFF;
  return f;
}

After — fill struct, call generated

Frame encode_status(state, ams_ok, bms){
  ifs08::AMS_status_t in{};
  in.fsm_state          = state;
  in.ams_ok             = ams_ok?1:0;
  in.module_online_mask = bms.module_online_mask;
  in.min_cell_mV        = bms.min_cell_mV;
  in.max_cell_mV        = bms.max_cell_mV;
  uint8_t b[8];
  ifs08::encode_AMS_status(in, b); // layout
  return detail::to_frame(b);      // from .def
}

The byte placement (which byte, big/little-endian) is gone from here — it now lives only in the .def. What stays is the mapping (which service field feeds which message field) and any value transform (the int8 temperature clip, the AMS_OK normalise, the cockpit bit-packing) — those are firmware concerns, not wire-layout.

4 · How we proved the wire didn't move

This is a safety-relevant path (the ECU/dash contract), so the bytes must be identical. Three layers of test, all green:

TestWhat it locks down
test_telemetry_encoders.cpp Hardcoded expected bytes (e.g. f[4]==0x12). These existed before the change and still pass against the DSL-backed code — that is the proof the switch is byte-for-byte identical.
test_dsl_parity.cpp Generated encoder == the field mapping, encode→decode roundtrips, registry well-formed. Covers every field shape: u8, BE-u16, LE-u32, signed-LE-i32, signed-LE-i8.
test_dsl_dbc_consistency.cpp The guard that never existed: every DSL descriptor must match the committed ams.dbc at the same bit position (length / order / sign). This finally checks C++ ↔ DBC.

Result: 205 / 205 host tests pass; firmware cross-compiles and links; flash-layout check passes.

The DBC, generated from the descriptors

tools/dbc_dump.cpp walks the same descriptors and prints DBC — the eventual replacement for gen_dbc.py:

BO_ 1184 AMS_status: 8 AMS
 SG_ fsm_state   : 0|8@1+  (1,0) "enum" Vector__XXX
 SG_ min_cell_mV : 39|16@0+ (1,0) "mV"  Vector__XXX   <- 8*4+7 = 39, big-endian

5 · Scope & what's next

Honesty about where this stops:

  • Done in Phase 2a: the 3 AMS telemetry frames (0x4A0/4A1/4A2) are fully on the DSL, live, and guarded against the DBC.
  • Not yet: gen_dbc.py still owns the DBC for the other ~37 messages, so the CI check is unchanged. We can't retire the Python until everything is ported.
PhaseWork
2bExtend the DSL with repeated/array fields, then port the pit-diag stream (0x6A0..0x6C8 — 200 NTCs row-major). The one message that needs new DSL capability.
3Port the remaining ECU-matrix frames (0x020, 0x135, 0x131..0x137…), then delete gen_dbc.py and swap the CI check to dbc_dump == committed — closing C++↔DBC for the whole bus.
