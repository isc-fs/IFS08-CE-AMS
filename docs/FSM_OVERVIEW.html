AMS finite state machine — full walkthrough

The FSM is stateless C++, header-only, no FreeRTOS/HAL dependency, 100 % unit-tested. MainTask calls fsm::step(Inputs) → Output every 20 ms and acts on the returned relay-action bitmask inline. State lives in MainTask's stack frame, never in the FSM itself.

§1Where the FSM sits in the system

Two mutually-exclusive contexts

Run and Charge are physically identical in relay configuration (AIR−, AIR+ closed, Precharge open). Only the FSM state byte distinguishes them. Downstream policies — BalanceController in particular — gate on the FSM state, so reading g_state_telemetry is the contract, not the relay state.

§3The Mode enum — locked once per boot

enum class Mode : std::uint8_t {
    Undecided = 0,    // before Start → Precharge has fired
    Car       = 1,    // VCU 0x100 heard within VcuFreshMs at the trigger
    Charger   = 2,    // VCU 0x100 silent at the trigger
};

Mode is set by MainTask, not by the FSM — the FSM only consumes it. Capture happens in safety_task.cpp at the exact 20 ms iteration that's about to fire Start → Precharge:

if (state == fsm::State::Start &&
    mode_locked == fsm::Mode::Undecided &&
    tsms && dash_chg) {
    const bool vcu_fresh =
        veh_snap.last_dc_bus_tick != 0u &&
        (now - veh_snap.last_dc_bus_tick) <= config::VcuFreshMs;   // 1000 ms
    mode_locked = vcu_fresh ? fsm::Mode::Car
                            : fsm::Mode::Charger;
}

Why decide externally?

The mode reflects a physical fact about the world (is this pack wired into a car or sitting on a charger?). A pack can't move between the two while the AMS is alive, so re-evaluating during Run/Charge would only let CAN noise or charger-side faults mis-route the FSM. Lock once, never re-evaluate.

Why 1000 ms?

VcuFreshMs is looser than VcuStaleMs=200 (the predicate's freshness gate) so that a slow VCU bring-up doesn't cause a Car-wired pack to be misclassified as Charger. Tightening would risk false-Charger; loosening would risk false-Car. 1 s is the agreed margin.

§4Inputs struct — what the FSM consumes

struct Inputs {
    State               current;            // current FSM state (mainline reads this)
    const BmsState&     bms;                // single-writer snapshot from BmsService
    const CurrentState& current_sensor;     // single-writer snapshot from CurrentService
    const VehicleState& vehicle;            // single-writer snapshot from VehicleService
    bool                tsms;               // PF9 readback (active-high)
    bool                dash_chg;           // PF10 readback (active-high)
    Mode                mode_locked;        // set by MainTask at Start to Precharge
    bool                force_error_set;    // legacy hook; no live setter
    std::uint32_t       now_tick;
    std::uint32_t       state_entry_tick;   // tick the current state was entered
};

now_tick - state_entry_tick gives the dwell time in the current state. Historically used by Precharge (1500 ms timeout) and Transition (100 ms hold) — both consumers retired in PR #244. state_entry_tick still arrives in the struct for ABI stability and future use; state_entry_tick is updated atomically with state in MainTask, so the FSM always sees a self-consistent pair.

Dead field — currently unused in body

After PR #244, no branch in fsm::step currently references state_entry_tick. The field is kept in Inputs for ABI stability (unit tests + SIL scenarios still populate it) and for the eventual "stuck-in-Transition watchdog" feature, but a static analyser will mark it as a dead input on this build. Worth removing or documenting if no near-term consumer surfaces.

Dead hook: force_error_set

The field is wired all the way through (Inputs → safety::evaluate_fault) but nobody ever sets it to true. MainTask always passes false. Either a placeholder for a future fault injector or dead code worth pruning. Leaving it in means tests can still exercise the "immediate-trip" path.

§5Output — next state + relay-action bitmask

struct Output {
    State         next;
    std::uint32_t safety_flags;  // bitmask of events::safety::*
};
1 << 0ForceErrorTelemetry marker. The actual safety effect comes from the Open* bits.
1 << 1CloseAirNapply_relay_actions → close AIR−
1 << 2CloseAirPclose AIR+
1 << 3ClosePrechargeclose precharge relay
1 << 4OpenAirNopen AIR−
1 << 5OpenAirPopen AIR+
1 << 6OpenPrechargeopen precharge relay

apply_relay_actions(out.safety_flags) in MainTask interprets each bit independently. There's no atomic "all open" macro — the three Open* bits get set together on every fault path. Open + close in the same mask for the same relay would be a bug; the code is structured so no transition emits both.

§6Two guards before the state switch

Guard 1 — sticky Error

if (in.current == State::Error) {
    return { State::Error,
             events::safety::ForceError };
}

Once in Error, you stay. Returns only ForceError — no Open* bits, because the relays were already opened at the original fault iteration. No point re-issuing GPIO writes every 20 ms.

Guard 2 — predicate fault trap

const safety::Inputs pred = {
    in.bms, in.current_sensor, in.vehicle,
    in.force_error_set, in.now_tick };
if (safety::evaluate_fault(pred)) {
    return { State::Error,
        ForceError | OpenAirN |
        OpenAirP | OpenPrecharge };
}

Any predicate fault preempts the normal transition logic, from any state. Predicate is HIL-agnostic; the boot grace lives inside the predicate, not here.

The predicate set (see safety_predicates.hpp)

  • force_error_set (immediate, even during boot grace)
  • now_tick < SafetyBootGraceMs (2000) short-circuits the rest of the predicate to false
  • BMS module_online_mask != AllModulesMask or any module stale > BmsStaleMs (1500)
  • Cell V outside [CellUVmV=2800, CellOVmV=4200] mV
  • Cell T outside [CellUTC=-10, CellOTC=60] °C
  • Current sensor_fault
  • Current stale > IStaleMs (200) — gated out under AMS_BMS_HIL_STUB
  • |filtered_mA| > ImaxMa (200 A)
  • VCU 0x100 stale > VcuStaleMs (200)

§7Per-state transition logic

Start — waiting for operator

if (in.tsms && in.dash_chg) {
    return { State::Precharge, CloseAirN | ClosePrecharge };
}
return { State::Start, 0u };
  • Edge: both GPIOs active simultaneously, level-polled at 20 ms cadence.
  • Action: AIR− closes + Precharge closes → current flows through the precharge resistor into the DC link.
  • Replaced GPIO since PR #187. Legacy was a CAN frame (0x600 start button OR 0x18FF50E7 charger detect). Both retired.
  • Mode capture is external. MainTask reads VCU 0x100 freshness at this exact iteration and writes mode_locked before calling fsm::step() — so by the time the FSM body sees Start → Precharge firing, the mode is already locked.

Precharge — charging the DC link

if (precharge_target_reached(in.bms, in.vehicle)) {
    return { State::Transition, CloseAirP | OpenPrecharge };
}
return { State::Precharge, 0u };

One exit: target reached → Transition (AIR+ closes, precharge relay opens). Precharge has no timed deadline — it waits indefinitely for V_target.

Deadline removed in PR #244

The previous body had a PrechargeMaxMs = 1500 ms hard timeout that forced Error on a stuck contactor. That deadline was redundant: the supervisor's freshness predicates (BmsStaleMs=1500, VcuStaleMs=200, IStaleMs=200) and range predicates (cell U/V, T) already catch every real-world failure mode in <= 1.5 s, via the predicate-fault trap that fires before the FSM's transition logic runs. Net effect: one fewer arbitrary constant, identical safety.

Precharge target math

inline bool precharge_target_reached(const BmsState& bms,
                                       const VehicleState& veh) {
    if (bms.pack_voltage_mV == 0u) return false;        // no-data guard
    const std::uint64_t bus_mV  = veh.dc_bus_V * 1000u; // V → mV
    const std::uint64_t pack_mV = bms.pack_voltage_mV;
    return bus_mV * 100u >= pack_mV * 95u;              // bus ≥ 0.95 · pack
}

Entirely in mV with uint64_t intermediates — overflow-safe even at 65535 V × 1000 × 100. The 0-mV guard handles the boot case where BmsPollTask hasn't written yet; without it, a zero-data pack would trivially satisfy bus·100 ≥ 0·95 and instantly jump to Transition with no actual precharge.

Transition — single-step passthrough

if (!precharge_target_reached(in.bms, in.vehicle)) {
    return { State::Error, ForceError | OpenAirN | OpenAirP | OpenPrecharge };
}
if (in.mode_locked == Mode::Car)     return { State::Run,    0u };
if (in.mode_locked == Mode::Charger) return { State::Charge, 0u };
return { State::Error, ForceError | OpenAirN | OpenAirP | OpenPrecharge };
  • Bus-still-up guard: dc_bus must STILL be ≥ 95 % of pack on this exact step. A momentary droop right after the contactor swap (precharge opened, AIR+ closed) lands in Error rather than energising the tractive system on a degraded bus.
  • Dispatch on mode_locked: Car → Run, Charger → Charge. Both transitions are zero-bit (no relay change — AIR+ already closed, precharge already open).
  • Undecided here is a programming error (would mean Transition reached without going through Start). Treated as fault for safety.

Hold timer removed in PR #244

The previous body had a TransitionHoldMs = 100 ms hold window during which Transition kept re-checking the bus. Now Transition is a one-FSM-step passthrough: AIR+ was just closed and precharge just opened on the Precharge→Transition edge, the next FSM tick (20 ms later) commits to Run or Charge. The bus-still-up guard remains so a failed contactor swap is caught instantly. Net effect: 100 ms faster Run/Charge entry, same safety semantics.

Run / Charge — terminal until fault

if (!in.tsms || !in.dash_chg) {
    return { State::Error, ForceError | OpenAirN | OpenAirP | OpenPrecharge };
}
return { State::Run /* or Charge */, 0u };

No timed exits. Either input dropping triggers a sticky Error (operator-mandated semantics: every AIR-open event survives the power cycle). The only way out of Run or Charge cleanly is to physically reach the next boot — and even then, you boot into Error unless the backup domain has lost power.

Error — defensive default

case State::Error:
default:
    // Already handled at function entry; defensive default.
    return { State::Error, events::safety::ForceError };

Reached only if an out-of-enum-range State ever appears. Belt-and-braces against undefined behaviour.

HIL stub deliberately violates the safety invariant

On flight builds the ErrorLatch is meant to be sticky — once set, only physical backup-domain power loss clears it. Under -DAMS_BMS_HIL_STUB the latch is wiped on every boot (VBAT-backed BKP1R outlives bench power cycles for tens of seconds). Never compile HIL_STUB into a flight image.

§10Cadence interaction in MainTask

The predicate runs at 10 ms (every iteration). The FSM runs at 20 ms (every other iteration). The IWDG refreshes on every clean iteration — including the latched-Error path, so the chip stays alive for diagnosis.

Predicate fires twice as fast as the FSM

A sensor going out of range causes relay-open within 10 ms, regardless of where in the 20 ms FSM cycle we are. force_error_set (if wired) would also bypass the 20 ms gate — immediate latch on the next predicate tick.

VBAT keeps the backup domain alive across software resets, watchdog resets, and brown-outs (so long as the VBAT cap holds — typically minutes on the carrier). Only full backup-domain power loss clears the latch in flight. On the bench, App_InitTask::clear() wipes it on every boot under HIL_STUB.

§12What you see on the wire per state

0x4A0[0] (FSM state byte) is emitted every 500 ms by MainTask's telemetry block:

0x00Startidle; TSMS+DASH_CHG=0 (or one of them); relays open; AMS_OK PB4=1
0x01PrechargeDC bus rising toward 0.95·pack_V; AIR− closed (relay LED 1), Precharge closed (LED 3); no deadline — stays until V_target or a freshness predicate trips
0x02Transitiondc_bus held at target for 100 ms; AIR− + AIR+ closed; precharge open

0x04Chargesteady state; on charging station; balancing eligible

Diagnostic discrimination

If you see byte 0x05 and sensible cell-V in 0x4A0[4..7] → chip alive, post-fault diag path. If you see 0x05 then telemetry goes silent → MainTask stuck (HardFault or stack overflow, not the latch). Different debug procedures.

§14Gotchas worth knowing

  1. Mode::Undecided reaching Transition is treated as a fault. Defensive: if a future refactor adds a path that skips Start (e.g. a "force-into-Precharge" diag command), it'll force-Error rather than silently default to Car.
  2. force_error_set is wired now (HIL-only). g_force_error_request in safety_task.cpp is a writable backdoor under AMS_BMS_HIL_STUB — Block B/C/D bench tests flip it to short-circuit the predicate to true on the next 10 ms tick. Flight builds compile the constant out (constexpr bool force_error_set = false).
  3. state_entry_tick is currently unused. Both consumers (Precharge timeout, Transition hold) were retired in PR #244. The field remains in Inputs for ABI stability and the eventual stuck-in-Transition watchdog feature.
  4. The FSM doesn't know about boot grace. That logic lives inside safety::evaluate_fault; the FSM body assumes the predicate result is authoritative. If you ever bypass the predicate trap (e.g. a debug "ignore predicates" flag), the FSM will happily try to transition with garbage data.
  5. Run and Charge are physically identical in relay configuration. Only the state byte distinguishes them. Downstream policies (BalanceController) gate on the FSM state — reading g_state_telemetry is the contract, not relay GPIO state.
  6. The 0-mV guard in precharge_target_reached is load-bearing. Without it, a zero-data pack would trivially satisfy bus·100 ≥ 0·95 and jump straight to Transition.
  7. State transitions are atomic with state_entry_tick updates. MainTask updates both in the same iteration, so the FSM always sees a self-consistent pair.
  8. The FSM never inspects current_sensor.charger_detected anymore. The field is dead — its only setter (AcuCanTask 0x18FF50E7 dispatch) was retired in PR #187. Mode is now decided exclusively by VCU 0x100 freshness.
  9. TSMS + DASH_CHG are level-polled, not edge-triggered. Holding both → Precharge will fire on the next 20 ms tick. Releasing either in Run/Charge → Error fires within 20 ms.
