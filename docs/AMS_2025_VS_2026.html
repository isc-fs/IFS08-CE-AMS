02What's the AMS, briefly

Same MCU (STM32H733), same job: keep the tractive-system pack safe and observable. The how changed radically.

2025bare-metal

A single main.cpp with a while(1) loop. Five hand-written classes (BMS_MOD, CPU_MOD, Current_MOD, Temperatures_MOD, plus a global state-machine module) own everything. CAN ISRs push frames into globals; the main loop polls timers and dispatches. No RTOS, no priority concept, no isolation.

while (1) {
  if (msg_acu_new) parse_acu(...);
  if (msg_bms_new) parse_bms(...);
  select_state();    // FSM tick
  send_telemetry();
  HAL_Delay(10);
}

2026FreeRTOS

Six tasks with explicit priorities + a pure-logic FSM in a header that the host unit-test build exercises directly. Services own mutex-protected state; tasks own scheduling. The supervisor task (SafetyTask) runs at 10 ms cadence and gates everything that can close an AIR.

for (;;) {
  last_wake += SafetyPeriodMs;    // 10 ms
  osDelayUntil(last_wake);
  auto bms_snap = BmsService::snapshot();
  if (evaluate_fault(...)) latch_error_();
  state = fsm::step(...);
  watchdog::refresh();
}
Why? Last season's bare-metal loop had no isolation between the BMS poll latency and the AIR-open response time — a long CAN burst from the slaves could delay an emergency open. With FreeRTOS the supervisor runs at osPriorityRealtime and preempts everything else, so AIRs open within one 10 ms tick of a detected fault regardless of what the BMS layer is doing.

03BMS communication — the big one

The biggest physical-layer change of the rewrite. Same five modules, completely different wire.

FDCAN2 polling

Each BMS slave was a separate microcontroller on its own CAN ID. The AMS polled them in turn over FDCAN2:

  • 5 modules × 6 frames per cycle = 30 RX frames per poll
  • One CAN bus dedicated just to the pack
  • One firmware per slave to maintain
  • Module addressing: 0x12C + 0x1E·m for module m
  • Slave responses parsed by BMS_MOD::parse() using ID ranges

LTC6811-1 isoSPI

The 5 modules now share a single daisy-chained isoSPI link driven by an LTC6820 master on SPI1. The AMS speaks to the chain directly — no slave firmware:

  • 10 LTC6811-1 ICs (2 per module) in series
  • Single CS line, one master, no per-slave CAN ID
  • PEC15 per IC at the wire level
  • FDCAN2 now bootloader-only — the BL claims it after a magic-reset jump for flash workflow
  • Code in ltc6811.hpp + ltc6820.hpp + bms_poll_task.cpp
Why? Removing the slave microcontrollers from the pack drops 5 firmware images and 5 sets of CAN dependencies. The LTC6811-1 + LTC6820 path is the BMS industry standard (Tesla, Rivian, AMP); maintenance becomes "read the datasheet" instead of "find the slave repo". The PEC15 wire-level check is also stricter than per-frame CAN CRC, so chain-integrity bugs surface before they corrupt cell readings.

06The six tasks

There were none in 2025. Each one in 2026 has a single, named responsibility.

SafetyTask
priority: Realtime · 10 ms
FSM step, predicate evaluation, watchdog refresh, telemetry emit. Preempts everything below.
BmsPollTask
priority: Normal · event-driven
Owns the LTC chain — ADCV broadcast, RDCV[A-D] reads, mux temperature sweeps, balancing WRCFGA writes.
AcuCanTask
priority: AboveNormal · queue-driven
Drains the FDCAN1 RX queue, dispatches VCU frames + BL trigger, runs the ECU TX matrix scheduler.
CurrentSensorTask
priority: AboveNormal · 50 ms
ADC3 polls of the SSA-2-250A current sensor on PF7. Calibrates once, then samples + filters.
App_InitTask
priority: High · single-shot
Brings up FDCAN1, LTC chain discovery + PEC validation, ErrorLatch init. Self-deletes after.
defaultTask
priority: Low · idle
CubeMX-generated, kept for completeness. Sleeps. Could carry future low-priority housekeeping.

07Testing

Going from "flash and pray" to a 149-test green wall on every PR.

2025

None. Every change required flashing the board and watching candump. Refactors were terrifying; regressions surfaced at the bench at 11 PM the night before testing days.

The only "test" was hardware-in-the-loop, ad-hoc, manual.

2026

  • 149 host-side unit tests in Unity, run in CI on every push
  • Pure-logic modules (FSM, predicates, encoders, LTC6811 decode, balance controller) tested without HAL
  • 5 end-to-end test_sil_* scenarios drive a full FSM cycle
  • HIL_STUB build flavour for bench tests against a Pi Pico LTC emulator
  • HIL acceptance plan (#245) gates v1.5.0 release on 6 test blocks A–F (boot, predicates, FSM, BL, LTC, flash endurance)
Why? Every confidence-breaking story from last season (the precharge ladder firing at the wrong threshold, the CAN ID confusion that put telemetry on the wrong bus) maps to "we couldn't test that without flashing". The unit tests catch them at make time; the bench is now for things you genuinely can't simulate (relay timing, real-pack EMI, charging behaviour).

09Build system

2025

STM32CubeIDE workspace. Build via the GUI. Linker scripts edited by hand. No version stamping. No CI.

Reproducing a flash from 3 weeks ago meant git checkout + clicking buttons in the right order.

2026

CMake from the command line. VERSION file is the semver source of truth; git rev-parse populates the firmware identity record at configure time.

# Flight build
cmake -B build \
      -DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# HIL build (Pico emulator on the bench)
cmake -B build-hil  -DAMS_BMS_HIL_STUB=ON

CI runs the cross-compile + unit tests on every push. Tag v1.5.x → GitHub Release with .elf / .bin / .hex attached.

10Rewrite milestones

A high-level walk through how 2026 got here.

v1.0 · early 2025
FreeRTOS skeleton + first telemetry
CubeMX baseline brought up under the new structure. 0x4A0..0x4A2 telemetry frames on FDCAN1 at 500 ms cadence.
v1.1 · mid 2025
Pure-logic FSM + safety predicates
State machine extracted into a unit-testable header. Predicate file consolidates "what counts as a fault" into one place with explicit per-rule tests.
v1.2 · #67–#75
BMS moves from CAN to LTC6811-1 isoSPI
The biggest physical-layer change. BmsRxTask retired, LTC6811 wire-format decoder + LTC6820 master driver shipped. FDCAN2 becomes bootloader-only.
v1.3 · #48
TSMS + DASH_CHG GPIOs replace 0x600 / 0x18FF50E7
Cockpit inputs become physical pins (PF9 / PF10) with pull-down defaults. Mode-lock (Car vs Charger) captured from VCU freshness at the moment of Start → Precharge.
v1.4 · #52, #53
Current sensor + ECU TX matrix
Bourns SSA-2-250A bipolar current sensor on PF7. ECU TX matrix (8 frames on FDCAN1) feeds the wireless telemetry uplink.
v1.5 · #207, #243, #247, #249, #252
Bench bring-up + production hardening
Pi Pico LTC emulator replaces the stub data source. Critical RX-DLC bug fixed (the BL trigger was silently dropped). Pit-diag runtime CAN stream lands. module_online_mask reflects current freshness. CMake-driven firmware identification. Ready for HIL acceptance.

11Reading order for new members

If you're picking this up cold, work top-to-bottom. Each step is ~30 min of reading.

1

The state machine

Core/Inc/app/state_machine.hpp — pure-logic, fits in one file. Six states, transitions in one switch. Start here.

2

The safety predicates

Core/Inc/app/safety_predicates.hpp — explicit "what counts as a fault". Boot-grace handling, BMS staleness, VCU heartbeat, cell V/T range.

3

The 6 tasks

docs/ARCHITECTURE.md §2 task table, then skim Core/Src/app/*_task.cpp. SafetyTask first, then BmsPollTask.

4

The CAN map

docs/CAN_MAP.md — every frame on FDCAN1, byte-by-byte. Skip the [LEGACY] sections; they're archaeology.

5

BMS chain protocol

docs/BMS_LTC6811.md + Core/Inc/app/ltc6811.hpp. Datasheet-driven; nothing magic.

6

HIL bench operating doc

docs/HIL_STUB.md — what flags exist, what each one relaxes, how to build for the bench.
