# AMS Firmware FMEA — Executive Summary

## 1. Overall Risk Posture

The AMS firmware exhibits a sound core safety architecture — independent fault predicates, a sticky error latch in RTC backup RAM, and locally-driven AIR/AMS_OK control that does not depend on CAN telemetry — but the verified FMEA reveals that residual risk is concentrated not in the safety *logic* but in its *preconditions and detection coverage*. The two highest-RPN findings (CONCURRENCY-03 RPN 216, CONCURRENCY-07 RPN 210) are both commissioning-integrity failures: the firmware ships with placeholder threshold and calibration constants and has no in-firmware guard that they were ever updated for the real pack, meaning a mis-commissioned unit can silently lose the under-voltage or over-current safety function. A second cluster (BOOT-02, BOOT-04, LATCH-01, RELAYS-05, MAINTASK-02) attacks the sticky-error contract itself: backup-register writes are issued without read-back verification and a HIL-only latch-clear flag has no build-time guard, so a latched fault can fail to survive a power-cycle and re-arm the pack in an unsafe state. The dominant systemic weakness is **detection (D)**: the great majority of findings carry D of 6–9 because GPIO/HAL/SPI writes are fire-and-forget with no read-back, and most failures surface only as lagging 500 ms pit-diag counters rather than as safety-loop predicates. Occurrence is generally low and many high-D items are also low-O (tick wraps, ECC bit-flips), keeping their RPN moderate, but their high severity (S 8–10) means they belong in the safety case regardless of RPN. Net assessment: the design is fundamentally fail-safe in its happy path, but it currently *trusts* commissioning data, hardware writes, and backup-domain integrity rather than *verifying* them — and that trust is the principal risk to close before flight.

## 3. Systemic Themes

1. **COMMISSION-value reliance with no in-firmware guard (highest leverage).** CONCURRENCY-03 and CONCURRENCY-07 — the two top RPNs — both stem from safety predicates trusting constants (thresholds, current gain/zero) that may still be placeholders or HIL-bench values. There is no static assert, no plausibility window, and no boot telemetry of active thresholds. A single class of defensive checks closes the two largest risks.

2. **Fire-and-forget hardware writes — no read-back / detection gap (most pervasive).** GPIO, HAL, and SPI writes are issued without verifying the hardware responded: relay closes (RELAYS-04, RELAYS-06, RELAYS-10, FSM-05, RELAYS-07), backup-register writes (BOOT-02, LATCH-01, RELAYS-05, MAINTASK-02), and LTC broadcasts (LTC-06). This is why so many findings carry D=6–9. The relay driver *exposes* `is_*_closed()` read-backs that the FSM never calls.

3. **Sticky-error / fail-safe-survival assumptions.** The sticky-error contract (ARCHITECTURE.md invariant 5) is assumed rather than enforced: BOOT-02, BOOT-04, LATCH-01, RELAYS-05, MAINTASK-02, FSM-07 all describe paths where a latched fault fails to survive a reset (write fails, ECC flip, HIL flag, IWDG races the write), re-arming an unsafe pack. These are low-O/high-S — RPN under-weights them relative to their place in the safety case.

4. **Lagging detection vs. the 10–15 ms safety loop.** Failures surface as 500 ms pit-diag counters, not safety-loop predicates: CAN_TX-01/07 (blind window), VEHICLE_RX-02 (queue-full drops), CURRENT-03 (ADC timeout), LTC-04/LTC-10 (per-channel/chain faults visible only to an external observer). Detection exists but lags the contractual fault-response window.

5. **32-bit tick wraparound / torn lock-free reads.** A coherent class of arithmetic-integrity bugs: unsigned tick wrap disables timeouts or staleness (CONCURRENCY-02, CONCURRENCY-05, PREDICATES-08, VEHICLE_RX-04, MAINTASK-03) and lock-free `snapshot()` can observe torn multi-field state (CONCURRENCY-01, CONCURRENCY-06, BALANCE-01). Low-O on a power-cycling race car, but trivially mitigated with the existing `tick_age()` helper pattern and worth eliminating as a class.

## 4. Prioritised Action List

**P0 — Commissioning integrity (close before any pack run):**
- CONCURRENCY-03: add a `static_assert`/runtime check that V/T/current thresholds differ from placeholders, plus a boot pit-diag frame emitting active thresholds so the bench confirms values before energising.
- CONCURRENCY-07: add a current-zero plausibility check (raw ADC ≈ 2048 ±200) wired to the existing CurrentSensorFault predicate, and emit commissioned gain/zero at boot tied to carrier part number (calibration is board-specific per VREF+).

**P1 — Enforce the sticky-error contract:**
- BOOT-04: add a CMake guard failing any Release/flight build with `AMS_HIL_CLEAR_ERROR_LATCH` set (and/or have MingoCAN refuse to flash an image carrying the flag).
- BOOT-02 / LATCH-01 / RELAYS-05 / MAINTASK-02: implement write-then-read-back verification on every ErrorLatch backup-register write; on mismatch, withhold the watchdog refresh to force a clean reset rather than re-arm. Order `ErrorLatch::set()` before `Relays::open_all()`.

**P2 — Add hardware read-back to safety-critical writes:**
- FSM-05 / RELAYS-07 / RELAYS-04 / RELAYS-06: call the existing `is_*_closed()` relay read-backs to confirm contactor swaps and closes; latch Error on mismatch instead of waiting out the 5 s precharge timeout.
- LTC-02 / LTC-04 / LTC-06: add a runtime chain-length re-check (RDCFGA echo) so daisy-chain desync routes to BmsModuleOffline instead of silent truncation; prefer PLADC polling to close the LTC-04 MOSI idle gap.

**P3 — Close detection / blind-window gaps:**
- CAN_TX-01 / CAN_TX-07: bounded retransmit (≤50 ms) for 0x4A0/4A1/4A2 and a consecutive-miss warning flag to shrink the ~500 ms ECU blind window on fault transitions.
- VEHICLE_RX-02 / CURRENT-03: surface RX queue-drop counts on telemetry; widen the 5 ms ADC poll timeout to ~20 ms to avoid false CurrentStale under load.
- MAINTASK-07: add an independent software watchdog (second timer ISR) that opens AIRs if the MainTask iteration count stalls — closes the invariant-3 gap where a refreshing-but-stuck task holds AIRs closed.

**P4 — Eliminate the arithmetic/torn-read class wholesale:**
- CONCURRENCY-02/05, PREDICATES-08, VEHICLE_RX-04, MAINTASK-03: replace naive tick subtraction everywhere with the existing wrap-safe `tick_age()` helper; add wrap-boundary unit tests.
- CONCURRENCY-01/06, BALANCE-01: add `volatile`/critical-section protection (or document debounce tolerance) for lock-free `snapshot()` torn reads.
- PREDICATES-06/09, MAINTASK-08: stop resetting the cell-debounce streak on unrelated faults so an interleaved fault pattern cannot indefinitely defer a real cell-fault latch.

**P5 — Backlog (availability/longevity, document or fix opportunistically):**
- BALANCE-02/03/04/07/08/09, FSM-08/FSM-01 (TSMS debounce), FSM-10 quantization, VEHICLE_RX-05/06/09 defensiveness. These do not open or hold AIRs unsafely; address as code-quality/availability work or document the intended behavior in ARCHITECTURE.md / COMMISSIONING.md.

**Cross-cutting documentation:** record in the safety case that the sticky ErrorLatch relies on STM32H7 backup-domain integrity (no ECC) — LATCH-01/BOOT-02 — and recommend a VBAT/supercap source on future carriers to retire that assumption.

## Detailed findings (RPN-ranked)

### CONCURRENCY-03 — Placeholder COMMISSION defaults (2800/4200/-10/60 mV/degC, 200 A) shipped without per-pack commissioning, so safety predicate thresholds may not match actual cell specifications or vehicle thermal/electrical design.

`🔴 High` · **RPN 216** (S9 · O6 · D4) · _Concurrency / config invariants_

- **Item:** config::CellUnderVoltageMv, CellOverVoltageMv, CellUnderTempC, CellOverTempC, CurrentMaxMa (ams_config.hpp:22-26)
- **Cause:** ams_config.hpp explicitly marks these as COMMISSION placeholders. No mechanism exists to validate these values at compile time or runtime. If team deploys firmware without running COMMISSIONING.md procedure, thresholds remain placeholders.
- **Local effect:** SafetyTask evaluates cell under/over-voltage and current over-limit predicates against incorrect thresholds.
- **System effect:** Under-threshold commissioning causes AIRs to fail to open on real cell under-voltage fault (safety function lost). Over-threshold commissioning causes spurious AIR opens during normal operation (availability loss). FS rules specify safe operating windows per cell; shipping with generic defaults risks both under-detection and false-trips.
- **Existing detection:** CONTRIBUTING.md and COMMISSIONING.md document procedure; codebase contains no automated check that values updated from placeholders.
- **Existing mitigation:** Documentation in COMMISSIONING.md and ams_config.hpp comments. Labelled COMMISSION, so values marked for attention. However, no enforcement: code will compile and run with placeholder thresholds unchanged.
- **Recommendation:** (a) Add static_assert or runtime check in app_init_task.cpp that verifies these constants differ from placeholders. (b) Add pit-diag telemetry frame that emits active thresholds so bench can confirm values before running pack. (c) Consider build flag requiring explicit per-vehicle threshold overrides. (d) Document in DEEP_DIVE.md that constants are vehicle-specific and must be commissioned per FS rules.
- **Verifier note:** REAL COMMISSIONING RISK: Lines 22-26 ams_config.hpp explicitly marked COMMISSION (2800/4200/-10/60 mV/degC, 200 A). No compile-time static_assert or runtime validation that values differ from placeholders. COMMISSIONING.md documents procedure but enforcement is documentary only. Finding correctly identifies: under-threshold = AIRs fail to open on real fault (safety loss); over-threshold = spurious opens (availability loss).

### CONCURRENCY-07 — Placeholder commissioned values are HIL-bench-specific (lines 311-314 detail calibration: +0.4% effective gain, +0.6 A zero offset from HIL #348). If flight hardware has different ADC VREF, capacitor tolerance, or sensor variance, zero/gain incorrect.

`🔴 High` · **RPN 210** (S7 · O6 · D5) · _Concurrency / config invariants_

- **Item:** config::CurrentZeroCount, CurrentMvPerAmpe1 (ams_config.hpp:318-319)
- **Cause:** Lines 318-319 mark these COMMISSION and explain nominal ideal would be 50/2048 but actual measured HIL values 2050/46. Code has no run-time calibration or verification that sensor operating within expected bounds.
- **Local effect:** Pack current mis-scaled. Example: if actual zero 2070 counts (3% higher than 2050 due to board tolerance), 0 A input reads as ~3 A (46 * (2070-2050)/10 = 92 mA, small error). For 200 A limit, 1% calibration error is ~2 A uncertainty.
- **System effect:** Current over-limit predicate compares filtered_mA against CurrentMaxMa. Mis-scaled current sensor allows pack to exceed 200 A without detection (under-threshold calibration, AIRs fail to open on real over-current), or spuriously triggers over-current faults (over-threshold, availability loss).
- **Existing detection:** COMMISSIONING.md §2 documents measurement procedure. No in-firmware validation that values plausible (e.g. zero offset should be within ±100 counts of 2048 = ADC mid-scale).
- **Existing mitigation:** Current sensor read every 50 ms, filtered with IIR low-pass (tau ~800 ms), compared against CurrentMaxMa with immediate-danger predicate (not debounced). 200 A transient <50 ms could be missed by raw ADC, but filtered value smooths momentary noise.
- **Recommendation:** (a) Add sanity-check helper in current_service.cpp verifying raw ADC count sits in expected window around CurrentZeroCount (e.g. 1900-2200 for zero=2048±200, catch open/shorted inputs). (b) Add CurrentSensorFault predicate if zero out of bounds (already implemented, current_service.hpp:23). (c) Document zero/gain calibration is per-assembly, must be re-measured if carrier PCB or ADC VREF component replaced. (d) Add boot-time telemetry frame emitting commissioned zero/gain so pit can confirm values match carrier part number.
- **Verifier note:** REAL CALIBRATION RISK: Lines 318-319 ams_config.hpp mark CurrentZeroCount=2050 and CurrentMvPerAmpe1=46 as COMMISSION with HIL#348 baseline. No sanity-check that measured zero is within plausible window (e.g., 1900-2200 for 2048±200). Field tolerance and VREF variation could shift actual zero by 1-3%, causing 2-5% scale error. CurrentSensorFault predicate exists but does not validate zero plausibility. Valid risk: under-threshold = AIRs fail on real over-current, over-threshold = spurious faults.

### BOOT-02 — Backup domain access unlock (DBP) succeeds but immediately fails, ErrorLatch read/write operates on uncorrected RTC register, latch state undefined

`🟠 Medium` · **RPN 162** (S9 · O2 · D9) · _Error latch + boot/init + bootloader iface_

- **Item:** error_latch.cpp:28-33 (ErrorLatch::init), safety_task.cpp:117-120 (MainTask init)

However: (1) the window is <100 ns (one BSRR cycle), (2) probability of ESD hitting exactly that window AND that specific pin is <<1 in a billion on a shielded automotive board, (3) both writes use BSRR (atomic at hardware level), and (4) non-GPIO ISRs cannot affect GPIO state. ### FSM-07 — Sticky Error latch combined with 'any-state error guard' (line 116) creates an unbreakable state if error_latched_ is set but the FSM isn't called (SafetyTask fault path skips FSM step)

`🟡 Low` · **RPN 12** (S3 · O1 · D4) · _FSM / state machine_

- **Item:** state_machine.hpp:116-118 (Error sticky semantics)
- **Cause:** SafetyTask has two paths: fault path (line 219-238) which skips FSM step entirely and just refreshes watchdog, and clean path (line 239-343) which runs FSM. If error_latched_ is true, the fault path is taken every iteration. The FSM is never called again. If error_latched_ is somehow cleared externally (e.g., a bench hack, invalid state corruption), the next FSM step at line 116 immediately returns Error again, ensuring it sticks. However, the real issue is: what if error_latched_ gets corrupted to false while ErrorLatch backup register still reads true? The FSM relies on error_latched_ flag (which is RAM-volatile) to sustain the Error state, but the backup register (RTC_BKP_DR1, persistent) is the source of truth. A RAM corruption of error_latched_ between boot and the first fault could cause desynchronization.
- **Local effect:** If error_latched_ RAM flag and ErrorLatch backup register diverge, the FSM state and the physical relay state can become inconsistent. E.g., error_latched_=false but RTC_BKP_DR1 set means the next power-on sees Error, but the current boot might show Start while relays are open.
- **System effect:** State inconsistency is latent but non-critical (relays are already open if Error is latched anywhere). On reboot, the correct state (Error) re-asserts from the backup register. But during the current boot session, telemetry might show incorrect state if error_latched_ and RTC are out of sync.
- **Existing detection:** NONE. The code does not periodically verify that error_latched_ and ErrorLatch::is_set() are consistent.
- **Existing mitigation:** PARTIAL. ErrorLatch::set() is called on every FSM Error entry (line 320) and predicate fault (line 228), so the backup register is updated synchronously. But there's no watchdog-like monitor to catch a RAM bit-flip of error_latched_ mid-session.
- **Recommendation:** Add a periodic consistency check (e.g., every 100ms, or part of the telemetry 500ms cycle) to verify error_latched_ == ErrorLatch::is_set(). - **Verifier note:** REAL but LOW-RISK. The volatile RAM flag error_latched_ (line 79, safety_task.cpp) and the persistent RTC backup register (ErrorLatch::set() at lines 228 + 320) can theoretically diverge if RAM is corrupted (bit-flip from radiation, brown-out, etc.). On the NEXT boot, the RTC is read and recovery is automatic (line 125-129). During the current boot, if error_latched_ is corrupted to false, the FSM can still emit Error (line 116-118, state_machine.hpp), and the next SafetyTask iteration would re-sync. However, there is NO periodic consistency check—this is a gap for safety-critical hardening. Severity 3 (late detection, not immediate hazard) vs analyst's 4. Mitigation: periodic CRC check of error_latched_ vs ErrorLatch::is_set().

### FSM-10 — DC-bus collapse detection compares `bus_mV * 100` to `pack_mV * BusCollapsePercent` using 64-bit arithmetic; integer division rounding can cause false negatives (bus appears higher than it is) if the pack voltage is very low or high

`🟡 Low` · **RPN 4** (S2 · O1 · D2) · _FSM / state machine_

- **Item:** state_machine.hpp:104-110 (bus_below_collapse detector: mV math precision)
- **Cause:** Lines 107-109 compute `(bus_mV * 100) < (pack_mV * BusCollapsePercent)`. If pack_mV is, e.g., 357,100 mV (95 cells × 3750 mV, a typical charged pack), and BusCollapsePercent is 50, the threshold is 17,855,000 mV. If bus_mV is 179 V (179,000 mV), then 179,000 * 100 = 17,900,000, which is >= 17,855,000, so the check returns false (not collapsed). But the actual ratio is 179 / 357.1 = 50.1%, which is just above the 50% threshold — on the edge. The math is correct, but the discrete quantization at low voltages (integer V to mV conversion, line 92) can introduce 1000 mV steps. If dc_bus_V is reported as 179 V (an integer) but the real voltage is 178.5 V, the rounding error hides a true collapse.
- **Local effect:** If the DC bus sags to exactly 50.0% of pack voltage, the detector may report 'not collapsed' due to rounding, missing the threshold by 1-2 ticks (10-20ms). The debounce (BusCollapseConfirmTicks = 20, line 251) would still require 20 ticks of continuous collapse before transitioning, so a single threshold-edge miss is absorbed.
- **System effect:** Low occurrence risk (bus sag is typically either >50% or <30%, not hovering at exactly 50%). But if it happens, the FSM misses one 10ms window of a bus-collapse event. If the bus only briefly grazes the 50% threshold and recovers, the debounce counter resets (line 257) and the event is not latched. This is a minor false-negative in bus-collapse detection, not a safety loss.
- **Existing detection:** NONE. The quantization error is inherent to the 16-bit uint16_t representation of dc_bus_V in volts.
- **Existing mitigation:** PARTIAL. The BusCollapseConfirmTicks debounce (20 ticks, ~200ms) is conservative and tolerates a few missed detections. A real bus collapse (AIRs opened externally) is a sustained condition lasting seconds, so a 10-20ms miss window is negligible.
- **Recommendation:** Document the quantization behavior in the code comment. For future enhancement: change dc_bus_V storage from uint16_t V to uint16_t (in 0.1V units, centi-volts), so 357.1 V is stored as 3571, eliminating the 1V quantization error. This is a COMMISSION-time change and would require CAN decoder updates. For now, the current approach is acceptable given the debounce.
- **Verifier note:** REAL but VERY LOW-RISK. The dc_bus_V is uint16_t volts (line 92, state_machine.hpp), introducing ~1V quantization error. However: (1) The math uses 64-bit uint64_t (line 107-109), so rounding within the comparison is minimal; (2) The BusCollapseConfirmTicks debounce is 20 ticks (~200ms, line 251), which absorbs a single-edge false negative; (3) A real bus collapse (AIRs opened externally, ARCHITECTURE.md §5 line 477-486) is a SUSTAINED condition (seconds), not a momentary edge. The quantization-edge case (bus at exactly 50% ±1V) is so rare that practical risk is negligible. Severity 2 (edge case only) vs analyst's 2. Mitigation: Future enhancement to store dc_bus_V in centi-volts (0.1V units) at COMMISSION time, requires CAN decoder updates.
